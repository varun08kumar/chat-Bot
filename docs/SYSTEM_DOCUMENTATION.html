Chat Bot Platform

A multi-provider chat application with an event-driven inference-logging pipeline underneath it. This document walks through every screen a user or operator sees, then the architecture that makes each one work - request lifecycle, auth, the crash-survivable job queue, and the Kubernetes deployment topology.

FastAPI · React · PostgreSQL Kafka · Redis Streams Prometheus · Grafana Docker Compose · Kubernetes

00 What this is

Two things layered on top of each other: a consumer-facing chat product, and the observability system built to watch it.

Users register, log in, and talk to whichever LLM provider is configured (Groq, OpenAI, Anthropic, or Gemini) through a single chat interface with real-time token streaming and an optional self-hosted web-search tool for current-events questions. Every inference call - regardless of provider - gets logged as a structured event, redacted, and persisted, so the platform can answer questions like "what's our p95 latency," "which provider is erroring," and "how much is this specific account using" without touching a single provider's own dashboard.

The two audiences are kept deliberately separate: a logged-in user only ever sees their own usage (in-app dashboard, scoped by their session). Cross-account visibility - "which user is driving up our Groq bill" - lives entirely in Grafana, behind Grafana's own admin login, never inside the product itself.

1.1 Why two separate paths to the same data

Both the in-app dashboard and Grafana's "Per-User Usage" view ultimately read the same inference_logs table, but they're built for different questions. The in-app one answers "how am I doing" and is gated by the caller's own JWT cookie - there's no way to ask it about someone else's account. Grafana answers "how is everyone doing" and lives behind a completely separate login; per-account labels on Prometheus metrics would mean unbounded cardinality at scale, so that view runs direct SQL against Postgres instead of going through Prometheus at all.

02 Chat request lifecycle

What actually happens between hitting send and a token appearing on screen - including the Redis job queue that decouples "accept the request" from "call the provider."

sequenceDiagram
    participant U as Browser
    participant N as nginx
    participant H as chat-service (request handler)
    participant PG as PostgreSQL
    participant Q as Redis Stream (chat:jobs)
    participant W as chat-service (background worker)
    participant L as LLM provider

    U->>N: POST /api/chat  (SSE, cookies + X-CSRF-Token)
    N->>H: proxy to chat-service:8001
    H->>H: verify access-token cookie + CSRF header
    H->>PG: persist the user's message
    H->>Q: subscribe to Pub/Sub channel for this request
    H->>Q: XADD job (conversation, model, messages)
    Q-->>W: XREADGROUP delivers the job
    W->>L: call provider, stream=true
    loop each token
        L-->>W: token chunk
        W->>Q: PUBLISH token event
        Q-->>H: relayed to the open SSE connection
        H-->>U: event: token
    end
    L-->>W: usage + finish
    W->>PG: persist the assistant's full reply
    W->>Q: XACK job (removes it from the pending list)
    H-->>U: event: done
→ the request handler never calls the LLM directly - it only enqueues and relays

The queue hop adds negligible latency in the common case (the same process's worker usually claims the job within milliseconds), and buys one real property: if the replica handling the HTTP connection crashes mid-response, the job is still sitting in Redis, unacknowledged, and any surviving replica's worker will finish it - see the next section.

2.1 Cancellation (the Stop button)

Because the LLM call now runs in a background worker rather than inline with the HTTP request, the old trick - closing the connection and letting Python's GeneratorExit unwind the call - no longer reaches the worker. Clicking Stop instead sets a short-lived chat:cancel:<request_id> flag in Redis; the worker checks it once per token and stops generating as soon as it sees it, persisting whatever was produced so far.

03 Crash-survival: orphaned job reclaim

What happens if the chat-service replica processing a request is killed mid-stream - verified by actually SIGKILL-ing a running container mid-request during testing.

sequenceDiagram
    participant Q as Redis Stream<br/>consumer group: chat-workers
    participant A as Replica A worker
    participant B as Replica B worker

    Q-->>A: job delivered, unacknowledged
    Note over A: process is killed mid-completion
    Note over Q: job stays in the Pending Entries List
    loop every 10s, every replica
        B->>Q: XAUTOCLAIM (idle > 30s)
    end
    Q-->>B: orphaned job handed to replica B
    B->>B: re-run the completion from scratch
    B->>B: persist assistant reply
    B->>Q: XACK
→ at-least-once, not exactly-once: a crash after the LLM call but before XACK can produce a duplicate reply on reclaim - accepted as the cheaper failure mode

04 Authentication

Two JWTs, both httpOnly cookies, plus a third non-httpOnly cookie for CSRF.

sequenceDiagram
    participant U as Browser
    participant C as chat-service

    U->>C: POST /auth/register or /auth/login
    C->>C: bcrypt hash / verify
    C-->>U: Set-Cookie access_token (3 min, httpOnly)
    C-->>U: Set-Cookie refresh_token (7 days, httpOnly)
    C-->>U: Set-Cookie csrf_token (7 days, readable by JS)

    loop every 2 minutes, while the tab is open
        U->>C: POST /auth/refresh (refresh_token cookie)
        C-->>U: rotates all three cookies
    end

    U->>C: POST /chat  (cookies auto-attached + X-CSRF-Token header)
    C->>C: verify access_token signature + expiry
    C->>C: compare X-CSRF-Token header to csrf_token cookie
→ refreshing every 2 minutes against a 3-minute access-token TTL leaves a 1-minute safety margin for a slow network hop

The CSRF check exists because httpOnly cookies are attached by the browser to any request to this origin, from any page - that's what makes CSRF possible even though the cookies themselves can't be read or stolen via script. The non-httpOnly csrf_token cookie can only be read by JavaScript actually running on this site, so a cross-site form has no way to produce a header that matches it.

06 Screens

Every screen a user or operator actually opens, in the order a new user would encounter them.

End user

01Log in

  • Submits email + password to POST /auth/login.
  • Identical error for "no such account" and "wrong password" - the form never reveals which emails are registered.
  • On success, receives three cookies (access, refresh, CSRF - see §4) and lands back in the chat.
  • Route is protected client-side too: any unauthenticated visit to /, /c/:id, or /dashboard redirects here automatically.
End user

02Sign up

  • Self-service - no invite, approval, or email verification step.
  • Password minimum 8 characters, hashed with bcrypt before it ever touches the database.
  • POST /auth/register returns 409 if the email already exists.
  • Successful signup logs the user straight in - same cookie-issuing flow as login.
End user

03Chat - empty state

  • Sidebar lists every past conversation for this account, grouped by day and searchable - fetched from GET /conversations, scoped to the caller's user_id.
  • Suggestion cards just pre-fill the composer with a canned prompt.
  • Model picker (bottom-left) persists the chosen model to localStorage across sessions.
  • Floating controls, top-right: dashboard toggle, light/dark theme, account menu.
End user

04Chat - active conversation

  • Message send goes through the full pipeline in §2: persisted immediately, queued, streamed back token-by-token over SSE.
  • Markdown renders live as tokens arrive (bold, lists, code blocks).
  • Footer shows real numbers pulled from the stream's own usage event - model, latency, prompt/completion/total tokens - not estimated.
  • A web_search tool fires automatically for time-sensitive questions (scores, prices, "latest…") via a self-hosted SearXNG instance; the system prompt explicitly tells the model when not to bother (math, definitions, general knowledge).
End user

05Account menu

  • Avatar is a computed initials-and-color badge, deterministic per email - there's no photo upload in this product.
  • Shows the signed-in email so there's never ambiguity about which account is active.
  • Log out clears all three session cookies server-side (not just client-side) and drops the cached session.
End user

06Personal dashboard

  • Requests, error rate, p95 latency, and token usage - for this account only.
  • metrics-service requires the same JWT cookie as chat-service and filters every query by the caller's user_id - one account can never see another's numbers here.
  • Latency, throughput, and error-rate charts are time-bucketed series over the selected window (15m–30d).
  • Provider/model tables break down the same window by what was actually used.
Operator

07Grafana - LLM Overview

  • Platform-wide operational health: request rate, error rate, latency percentiles, requests by provider - across every user combined.
  • Sourced straight from Prometheus, which scrapes a /metrics endpoint on chat-service and metrics-service directly (not through Postgres).
  • Gated by Grafana's own admin login - a regular product account has no access to this page at all.
Operator

08Grafana - Cluster Overview

  • Kubernetes-level health across every deployment in the namespace - not just chat-service's HPA (that view exists separately, for load-testing).
  • Nodes ready, running pods, container restarts (flags crash loops), and requested-vs-allocatable CPU/memory for the whole namespace.
  • Fed by kube-state-metrics, which reads pod/deployment/node state straight from the Kubernetes API and exposes it as Prometheus metrics.
  • The replica-status table merges four separate PromQL queries (desired/available/ready/updated) into one row per deployment.
Operator

09Grafana - Per-User Usage

  • The one place cross-account visibility exists: which registered account used how much, of which provider and model.
  • Deliberately not in Prometheus - a per-user label on a scraped metric means unbounded cardinality once real accounts pile up. This dashboard runs raw SQL against Postgres instead, via a dedicated Grafana datasource.
  • A template variable at the top lets an operator filter down to one or several accounts; left on "All," the top table always shows the full roster, including accounts with zero activity.
Operator

10Kafka UI

  • Operational visibility into the event pipeline itself, independent of the app.
  • Every inference call chat-service makes is published as an event to the inference.logs topic.
  • consumer-service reads that topic, redacts PII, and writes structured rows into Postgres - which is what both the personal dashboard and the two Grafana usage views ultimately read.
